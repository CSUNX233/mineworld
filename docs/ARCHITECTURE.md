# 模块结构与推进建议

本轮采用渐进拆分。`Game` 仍负责运行时编排与部分菜单，地图、遭遇进度、专精规则、投射物运动、配置和存档迁移已有独立入口。

## 职责与边界

| 模块 | 当前入口 | 负责内容 |
| --- | --- | --- |
| 游戏流程 | `core/Game.ts`、`EncounterDirector.ts` | 主菜单、开局、房间状态、暂停、层间选择、死亡 |
| 战斗 | `player/CombatSystem.ts`、`combat/ProjectileSystem.ts` | 攻击查询、投射物运动与碰撞；伤害结算和效果触发仍由 Game 编排 |
| 角色 | `player/`、`monsters/` | 控制、属性、动画、怪物行为与房间生成 |
| 地图 | `world/FloorGenerator.ts`、`Navigation.ts`、`data/rooms.ts` | 房间图、模板、共享寻路、房间标记 |
| 成长经济 | `items/`、`data/builds.ts`、`data/talents.ts` | 装备、词条、套装、商店、打造、专精与天赋配置 |
| 画面声音 | `world/World.ts`、`core/Effects.ts`、`core/AudioManager.ts`、视图模型 | 渲染、特效、镜头与音频 |
| 界面输入 | `ui/`、`core/InputManager.ts` | HUD、背包、专精选项、键鼠与触屏输入 |
| 数据存档 | `types.ts`、`data/`、`core/SaveManager.ts`、`SaveMigrations.ts` | 内容配置、序列化和版本迁移 |

配置不引用界面或 Game。`EncounterDirector` 只维护房间状态，返回需要生成或完成的房间，由 Game 执行奖励、渲染和存档。`ProjectileSystem` 返回碰撞结果，由调用方决定伤害和特效。这样可以单独验证规则，避免规则层依赖 DOM 或整个运行时。

## 当前一层的体验

入口 → 主线战斗 → 出口战斗 → 专精 → 下一层。两个主线房清理完成即可离开。外围环路提供精英、宝藏、恢复与额外战斗，可以按构筑和资源决定是否探索。商店是独立的地图交互格，生成在宝藏或恢复房的空闲位置；每三层保底一次，其余楼层 35% 概率出现，不占用传送门或扩大地形。独立随机数序列保持旧地图几何和存档坐标稳定。

地图固定为 40×40、9 个房间。随机性来自旋转、连接、障碍模板和遭遇组合。难度增加通过敌人组合和数值实现；后续优先增加带机制的房间模板与事件，保持通行轴清楚，避免用面积延长单局。

专精每层选一次，各最多三级：近战第三次命中触发震荡与护盾；火系命中触发范围灼烧并缩短火球冷却；召唤专精通过击杀召唤与回蓝形成循环。装备、套装和天赋仍可叠加。

## 性能与状态约定

- 普通房间进入时生成 3–4 个敌人，避免开局生成整层敌人；同时激活多个房间时敌人仍可能累积。
- HUD、技能状态与小地图每 0.1 秒刷新；输入、碰撞、动画和战斗效果逐帧处理。
- 装备属性与特殊词条缓存由穿戴、卸下和整体替换使其失效。新增装备变更应走 EquipmentManager，额外属性采用新对象替换，避免原地修改使缓存过期。
- 设置首次读取后缓存在内存，更新走 SettingsManager，镜头计算无需反复访问 localStorage。
- 同一地图、同一玩家目标格的怪物共享 BFS 距离场，玩家跨格时更新；动态地形若加入，需要增加导航缓存失效机制。
- 以上减少了热路径工作量，尚未在真实手机上测量帧率；不能据此宣称固定 FPS 提升。

## 存档与验证

版本 2 增加遭遇状态、怪物所属房间、宝箱、恢复房和专精进度。版本 1 保留角色与经济数据，重建当前楼层，避免旧地图坐标与新房间图混用。

`npm test` 包含 800 张种子/楼层组合的连通性与路径约束、流程恢复、专精限制、装备缓存、导航和旧存档迁移。浏览器回归另覆盖真实专精按钮、换层、宝箱恢复、手机背包与多指操作。

## 后续推进

1. 战斗：将 Game 中伤害、状态和专精触发拆成独立结算服务，统一一次命中产生的伤害、击退、状态和表现事件；先固定现有行为，再加入新的敌人机制。
2. 探索：在固定空间预算内增加路线风险、机关和可交互事件；统计主线路程、回头路与单层耗时，用数据调整模板。
3. 构筑：增加改变技能行为的装备与互斥选择，测量各专精成型时间和清房效率，避免只增加数值等级。
4. 流程与界面：商店视图已移入 `ui/ShopUI.ts`，经济规则位于 `items/ShopSystem.ts`；继续提取角色面板，最后统一暂停、死亡、结算等状态转换。
5. 表现与性能：在目标手机实测 CPU/GPU 帧耗时，再决定实例化、特效池、阴影与画质分档的优先级。

## 商店经济与背包操作

商店定位是补齐部位和把多余掉落转成推进资源。采用金币，不新增专属货币。四件货架至少提供一件魔法和一件稀有装备；随机委托选部位，前四层魔法 75% / 稀有 25%，第五层起魔法 72% / 稀有 25% / 史诗 3%，不产出传说。每层最多三次换货、三次委托、两次恢复，换货不重置其他次数，售罄不会自动补货。

定价基准为零幸运、只走主线的预期金币：两次清房奖励，加六或八只普通怪的平均金币，不包含额外掉落出售、支路、Boss 和幸运加成。第 1 层约 66，第 3 层约 122，第 5 层按普通遭遇估算约 224。首次换货约为本层基准的 20%，之后线性递增；恢复 40% 生命与法力约需基准的 25%。定向委托取基准 65% 与保守预期回收价值 135% 的较高值。直接购买价格至少是装备出售/分解材料出售两种回收价值较高者的 125%，防止立即买入再回收套利。委托可能偶尔抽到价值高于价格的装备，但次数有限、平均回收值低于成本。

这些是首轮数值约束，不代表已完成长期平衡。后续应记录金币结余、购买率、支路访问率和委托使用率，调整价格与货架品质。参考了 [Diablo III 的卡达拉随机装备消费](https://news.blizzard.com/en-us/article/22989464/legendary-an-ancient-primal-guide) 与 [Last Epoch 的阵营交易设计](https://forum.lastepoch.com/t/trade-item-factions/61722)；当前不引入跨局商人声望。

背包仅负责整理、穿戴和打造/分解。批量分解先预览数量与材料，确认时只处理预览中的物品，不处理已穿戴装备。整理保持物品对象不变，按品质降序、部位顺序、等级降序排列。出售入口集中在商店，交易后立即保存。
